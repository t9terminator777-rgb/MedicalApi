# MedicalApi с PostgreSQL и EF Core

## Локальный запуск

Нужны .NET 10 SDK, PostgreSQL и pgAdmin. В pgAdmin подключитесь к локальному серверу и создайте две учебные базы.

| База | Что выполнить |
| --- | --- |
| `clinic` | Откройте Query Tool в пустой базе и выполните [clinic.sql](sql/clinic.sql). Файл создаёт таблицы, заполняет их учебными данными и содержит ручные запросы. Выделяйте отдельные `SELECT`, чтобы увидеть их результаты. Проверки ограничений выводят сообщения во вкладку **Messages**. |
| `medical` | Примените миграции командами ниже. Затем в Query Tool выполните [catalog.sql](sql/catalog.sql), чтобы добавить четыре вида справок для демонстрации. |

Из папки с `MedicalApi.csproj` выполните команды в PowerShell. Подставьте пароль своего пользователя PostgreSQL.

```powershell
dotnet user-secrets set 'ConnectionStrings:Medical' 'Host=localhost;Port=5432;Database=medical;Username=postgres;Password=...'
dotnet tool restore
dotnet ef database update
dotnet run --launch-profile http
```

Откройте [Swagger](http://localhost:5046/swagger). В pgAdmin раскройте `medical → Schemas → public → Tables`. Там будут `Patients`, `SpravkaTypes`, `Spravki` и `Appointments`.

## Что показать на паре

1. Через `POST /api/Patients` создайте пациента. Поле `id` можно дописать в тело вручную, чтобы показать, что база выдаёт свой номер. Ответ должен содержать HTTP 201 и созданный `id`.

   ```json
   {
     "id": 9999,
     "name": "Учебный Пациент",
     "birthDate": "2002-04-12",
     "email": "patient@example.com"
   }
   ```

2. Найдите пациента через `GET /api/Patients?name=Учебный` и в Query Tool базы `medical`. Замените `1` на номер, полученный в ответе на POST. Имена таблиц и столбцов из миграций EF Core пишутся в двойных кавычках.

   ```sql
   SELECT "Id", "Name", "BirthDate", "Email"
   FROM "Patients"
   WHERE "Id" = 1;
   ```

3. Вызовите `GET /api/SpravkaTypes` и выберите вид справки. Дважды вызовите `POST /api/Spravki`, подставив полученные номера пациента и вида. Пример тела запроса для номеров 1 и 1.

   ```json
   {
     "patientId": 1,
     "spravkaTypeId": 1
   }
   ```

4. Вызовите `DELETE /api/Patients/{id}` и проверьте HTTP 400. Повторный `GET /api/Patients/{id}/spravki` должен вернуть обе справки. Для используемого вида справки `DELETE /api/SpravkaTypes/{id}` должен вернуть HTTP 409.
5. Покажите команды EF Core в консоли после POST и GET. В [ef-queries.sql](sql/ef-queries.sql) собраны примеры команд из журналов. Для сравнения с ручным SQL вызовите `GET /api/Stats`.

## Решения и наблюдения

- `Init` создаёт таблицы и связи, `AddPatientEmail` добавляет необязательный `Email`, `RestrictCertificateDeletion` защищает выданные справки. После добавления столбца существующие записи получают `NULL`. Обязательные поля имеют ограничение `NOT NULL`. Дата рождения и дата выдачи хранятся как `date` и представлены в C# типом `DateOnly`, цена хранится как `numeric(10, 2)` и представлена типом `decimal`.
- Справка сохраняет название вида и цену на момент выдачи. Связи `ON DELETE RESTRICT` защищают её при попытке удалить пациента или используемый вид. API заранее проверяет наличие справок через `AnyAsync`. Если удаление пациента разрешено, его записи на приём (`Appointments`) удаляются каскадно.
- Модели запросов на создание не принимают `Id`. PostgreSQL назначает первичный ключ при вставке. Без `SaveChangesAsync` контекст только отслеживает новый объект. `INSERT` отсутствует в журнале, запись отсутствует в GET и pgAdmin, а ответ POST может содержать `201` с `id = 0`.
- Когда `Where` и `OrderBy` стоят перед `ToListAsync`, EF Core переводит их в `WHERE` и `ORDER BY` PostgreSQL. После `ToListAsync` LINQ обрабатывает загруженный список в памяти. `CountAsync` и `SumAsync` дают SQL-агрегаты `COUNT` и `SUM`. `COUNT(*)` считает строки, а `SUM(price)` суммирует цены выданных справок.

## Проверено на PostgreSQL 18.6

Применены все три миграции. На этапе `Init` удаление пациента удалило две связанные справки. После `AddPatientEmail` существующая запись получила `NULL` в столбце `Email`. В итоговой схеме API вернул 400 при удалении пациента со справками и 409 при удалении используемого вида. Обе справки сохранились.

Пациент и справки остались доступны после перезапуска API. Прямой `UPDATE` в PostgreSQL стал виден через GET. При изменении телефона EF Core записал в SQL только столбец `Phone`. Повторный PUT с тем же телом выполнил только SELECT.

В ручной базе `clinic` проверены 8 пациентов, 5 видов и 12 выданных справок на 3050.00. В ноябре 2026 года выдано 7 справок на 1550.00. PostgreSQL отклонил все четыре операции с нарушением ограничений.

В отдельной проверочной копии POST без `SaveChangesAsync` вернул HTTP 201 с `id = 0`. В базе и в ответе GET записи не было, журнал не содержал INSERT. Фильтр `Price > 300` до и после загрузки дал одинаковый результат. В SQL первого варианта было условие WHERE, во втором PostgreSQL вернул все справки для обработки в C#.
